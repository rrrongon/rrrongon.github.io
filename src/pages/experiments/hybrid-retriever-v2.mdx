## 1. Benchmark Dataset (`v2.0`)

To benchmark retrieval quality without relying on generic public leaderboards, this project uses a versioned golden dataset (`data/golden_dataset.json`, `v2.0`). It separates the searchable knowledge base (`documents`) from labeled test cases (`queries`), enabling deterministic, repeatable regression testing across retrieval configurations.

### Corpus (22 Technical Documents)

The corpus simulates an ML infrastructure and production operations knowledge base engineered with **hard-negative distractor clusters**—groups of documents that share nearly identical templates and differ only by an error code, exit signal, SKU, or CLI flag:

| Doc IDs | Domain Cluster | Count | Purpose in Evaluation |
| :--- | :--- | :---: | :--- |
| `doc_01` – `doc_03` | LLM Inference & Vector Math | 3 | Tests conceptual phrasing (PagedAttention, continuous batching, L2 normalization). |
| `doc_04` – `doc_09` | Connection Pool Errors (`ERR_4091`–`4096`) | 6 | Hard negatives with identical prefixes (*"Worker node connection pool exhausted..."*) differing only in error code and remediation. |
| `doc_10` – `doc_13` | Container Exit Codes (`EXIT_137`–`255`) | 4 | Hard negatives with identical opening phrasing (*"Container terminated abruptly by host kernel..."*). |
| `doc_14` – `doc_17` | Hardware Parts (`SKU-901A`–`901D`) | 4 | Tests exact alphanumeric SKU discrimination across similar hardware specs. |
| `doc_18` – `doc_20` | vLLM CLI Flags (`--max-*`, `--gpu-*`) | 3 | Tests hyphenated flag retention alongside overlapping GPU memory terms. |
| `doc_21` – `doc_22` | Billing & Eval Operations | 2 | Zero-keyword-overlap paraphrase targets (Terminate Subscription, JSONL offline scoring). |

### Labeled Query Suite (14 Queries)

Each query maps to one ground-truth `expected_doc_id` and is tagged by `category` so aggregate metrics cannot hide localized failure modes:

* **`semantic` (`q01` – `q04`, 4 queries):** Natural-language questions using synonyms and paraphrases with little or no exact word overlap with the target document (e.g., *"How do I stop my yearly membership from auto-renewing?"* $\rightarrow$ `doc_21`). Tests conceptual alignment and asymmetric `query:` / `passage:` prefixes.
* **`exact_id` (`q05` – `q14`, 10 queries):** Troubleshooting and spec lookups containing exact identifiers (`ERR_4094`, `EXIT_139`, `SKU-901B`, `--max-model-len`). Tests whether dense embeddings blur exact tokens inside near-duplicate clusters—and how hybrid search resolves them.

## 2. Evaluation Metrics

Every retrieval configuration returns the top $K = 3$ document IDs per query and is scored deterministically across four metrics:

### 1. Recall@3
* **What it tells us:** Whether the retriever found the correct document anywhere inside the top 3 results (retrieval coverage), regardless of whether it landed at rank #1, #2, or #3.
* **How to compute:** Give `1.0` if `expected_doc_id` is in the top 3 retrieved IDs, and `0.0` otherwise; then take the average across all $N$ queries:

$$\text{Recall@3} = \frac{1}{N} \sum_{i=1}^{N} \mathbf{1}(\text{expected}_i \in \text{top3}_i)$$

* **Simple example (3 queries):**
  * Query A: Expected doc is at Rank #1 $\rightarrow 1.0$
  * Query B: Expected doc is at Rank #3 $\rightarrow 1.0$
  * Query C: Expected doc is at Rank #5 (not in top 3) $\rightarrow 0.0$
  * $\text{Recall@3} = \dfrac{1.0 + 1.0 + 0.0}{3} = \mathbf{0.67}$

### 2. MRR@3 (Mean Reciprocal Rank)
* **What it tells us:** How high the retriever ranks the correct document (ranking precision). Unlike Recall@3, MRR@3 rewards putting the right answer at #1 rather than burying it at #2 or #3.
* **How to compute:** Take $\frac{1}{\text{rank}}$ of the expected document if it appears in the top 3 (`1.0` for #1, `0.50` for #2, `0.33` for #3) or `0.0` if missed, then average across all $N$ queries:

$$\text{MRR@3} = \frac{1}{N} \sum_{i=1}^{N} \text{RR}_i, \quad \text{where } \text{RR}_i = \begin{cases} \dfrac{1}{\text{rank}_i} & \text{if } \text{expected}_i \in \text{top3}_i \\ 0 & \text{otherwise} \end{cases}$$

* **Simple example (same 3 queries):**
  * Query A (Rank #1): $\frac{1}{1} = 1.00$
  * Query B (Rank #3): $\frac{1}{3} = 0.33$
  * Query C (Missed top 3): $0.00$
  * $\text{MRR@3} = \dfrac{1.00 + 0.33 + 0.00}{3} = \mathbf{0.44}$

### 3. Semantic MRR
* **What it tells us:** How well the retriever understands conceptual meaning and paraphrases when exact keywords do not match.
* **How to compute:** Filter the evaluation set to only `category == "semantic"` queries (`q01`–`q04`), then compute MRR@3 on that subset.
* **Simple example (4 semantic queries):**
  * `q01` (Rank #1 $\rightarrow 1.00$), `q02` (Rank #1 $\rightarrow 1.00$), `q03` (Rank #2 $\rightarrow 0.50$), `q04` (Rank #1 $\rightarrow 1.00$)
  * $\text{Semantic MRR} = \dfrac{1.00 + 1.00 + 0.50 + 1.00}{4} = \mathbf{0.88}$

### 4. Exact-ID MRR
* **What it tells us:** How reliably the retriever preserves exact alphanumeric identifiers (error codes, exit signals, SKUs, CLI flags) without confusing them with near-duplicate documents.
* **How to compute:** Filter the evaluation set to only `category == "exact_id"` queries (`q05`–`q14`), then compute MRR@3 on that subset.
* **Simple example (4 exact-ID queries):**
  * `q05` (Rank #1 $\rightarrow 1.00$), `q06` (Missed top 3 $\rightarrow 0.00$), `q07` (Rank #2 $\rightarrow 0.50$), `q08` (Rank #1 $\rightarrow 1.00$)
  * $\text{Exact-ID MRR} = \dfrac{1.00 + 0.00 + 0.50 + 1.00}{4} = \mathbf{0.63}$

## 4. Retrieval Methodology & Asymmetric Search

To understand where lexical and neural search succeed or fail on our v2.0 benchmark, we evaluate three retrieval strategies served via **vLLM** (`intfloat/e5-small`, `runner="pooling"`).

### 4.1 Dense Semantic Retrieval (vLLM Pooling)
- **How it works:** Dense retrieval maps text into a continuous vector space to capture conceptual meaning rather than exact word overlap:
  1. **Tokenization & Single Forward Pass:** Input text is split into subword tokens and passed through `intfloat/e5-small` (a 12-layer bidirectional transformer encoder combining self-attention and feed-forward layers). With `runner="pooling"`, vLLM skips autoregressive token decoding and runs a single prefill forward pass.
  2. **Mean Pooling:** Token-level hidden states are averaged into a single **384-dimensional** dense vector representing the entire chunk.
  3. **L2 Normalization & Dot Product:** Vectors are normalized to unit length ($\|\mathbf{v}\|_2 = 1$). Because unit vectors have magnitude `1`, cosine similarity simplifies to a fast matrix dot product:

$$
\text{sim}(\mathbf{q}, \mathbf{d}) = \mathbf{q} \cdot \mathbf{d}
$$

- **Strength & Limitation:** Understands synonyms and paraphrased ideas easily, but often confuses near-duplicate documents that differ only by an exact number or error code.

### 4.2 Sparse Lexical Retrieval (BM25)
- **How it works:** To overcome the tendency of dense embeddings to blur rare tokens and exact identifiers, we use **Best Matching 25 (BM25)**. BM25 is a statistical, exact-match sparse retrieval algorithm—not a neural embedding model. It scores documents by matching exact tokens (preserving underscores and hyphens via regex `r"[a-z0-9_-]+"` so identifiers like `err_4094` and `--max-model-len` remain intact).
- **Scoring mechanics:** It rewards rare, high-signal terms via **Inverse Document Frequency (IDF)**, caps repeated words using **Term Frequency (TF) saturation**, and normalizes for document length.
- **Strength & Limitation:** Unbeatable for exact alphanumeric identifiers (`ERR_4094`, `SKU-901B`), but fails completely (`0.0` score) on paraphrased queries that share zero keywords with the target document.

## 5. Baseline Ablation Analysis: Dense vs. BM25

| Experiment | Recall@3 | MRR@3 | Semantic MRR | Exact-ID MRR |
| :--- | :---: | :---: | :---: | :---: |
| **Dense (no prefixes)** | 0.79 | 0.62 | 0.88 | 0.52 |
| **BM25 only** | 0.93 | 0.86 | 0.50 | 1.00 |

### 5.1 Dense Retrieval (No Prefixes)
- **What it is:** Neural semantic search using `intfloat/e5-small` via **vLLM** (`runner="pooling"`). Raw query and document strings are converted into 384-dimensional L2-normalized vectors without `"query: "` or `"passage: "` task prefixes, and ranked by dot-product similarity.
- **What the numbers show:**
  - **Overall coverage & rank:** Dense found the expected document in the top 3 **79%** of the time (`11 / 14` queries), with an `MRR@3` of **0.62**.
  - **Strong conceptual matching (`Semantic MRR = 0.88`):** On paraphrased queries (`q01`–`q04`), Dense ranked 3 out of 4 targets at #1 and 1 target at #2 (`(1.0 + 1.0 + 1.0 + 0.5) / 4 = 0.88`), bridging synonyms like *VRAM* and *memory* without needing exact keyword overlap.
  - **Exact-identifier collapse (`Exact-ID MRR = 0.52`):** On strict code lookups (`q05`–`q14`), performance dropped sharply because subword tokenization blurs arbitrary numbers (`ERR_4091`–`ERR_4096`, `SKU-901A`–`901D`) inside near-identical sentence templates.

### 5.2 BM25 Only (Sparse Lexical Retrieval)
- **What it is:** A statistical, exact-match keyword ranking algorithm (`BM25Okapi`) that scores documents based on shared tokens (preserving underscores and hyphens via regex `r"[a-z0-9_-]+"`), boosting rare terms via IDF and capping repeated words via TF saturation.
- **What the numbers show:**
  - **Overall coverage & rank:** BM25 found the expected document in the top 3 **93%** of the time (`13 / 14` queries), with an `MRR@3` of **0.86**.
  - **Perfect identifier precision (`Exact-ID MRR = 1.00`):** Every single exact-ID query (`10 / 10`) landed at Rank #1 because unique tokens like `err_4094` and `sku-901b` carry high IDF weight while shared boilerplate words are discounted.
  - **Semantic blind spot (`Semantic MRR = 0.50`):** On conceptual queries (`q01`–`q04`), BM25 dropped to **0.50** (missing top-3 completely on 1 zero-keyword-overlap query and ranking 2 others at #2), because it has no understanding of synonyms or paraphrased intent.

### 5.3 Two Key Takeaways Beyond the Headline Numbers

1. **Aggregate Metrics Can Be Misleading (Dataset Slice Skew):** Looking only at overall `Recall@3` (`0.93` vs. `0.79`) makes BM25 appear strictly superior to Dense. However, 10 of the 14 queries (71%) in `v2.0` are `exact_id` lookups. Slicing metrics by query category exposes BM25's `0.50` failure on semantic queries that aggregate averages would otherwise hide.
2. **The Recall–MRR Gap Reveals "Cluster Confusion" in Dense Search:** For Dense (no prefixes), `Recall@3` is `0.79` while `MRR@3` drops to `0.62` (a `0.17` gap). This shows that Dense usually retrieves the right topic cluster into the top 3 (e.g., returning `ERR_4091`, `ERR_4092`, and `ERR_4094` together), but lacks the token-level sharpness to place the exact target at Rank #1.


### 5.4 Asymmetric Prefixes: Closing the Semantic Gap

In our baseline experiment, **Dense (no prefixes)** achieved a `Semantic MRR` of **0.88**—meaning 3 out of 4 conceptual queries landed at Rank #1, while 1 landed at Rank #2. Before addressing exact-ID collisions, our first hypothesis was to test whether we could push conceptual retrieval to **1.00** by fixing how the model encodes questions versus documents.

When we pass raw text into `intfloat/e5-small`, the encoder treats a short, open-ended user question (*"How do I stop my yearly membership from auto-renewing?"*) and a longer declarative document (*"To cancel a recurring annual plan..."*) as the exact same type of text. However, `e5-small` was trained with explicit task prefixes—`"query: "` for search inputs and `"passage: "` for indexed documents—to bridge this structural asymmetry in vector space. By supplying those prefixes, we hypothesized the model would align questions with their answers more tightly and eliminate the remaining semantic ranking error.

| Experiment | Recall@3 | MRR@3 | Semantic MRR | Exact-ID MRR |
| :--- | :---: | :---: | :---: | :---: |
| **Dense (no prefixes)** | 0.79 | 0.62 | 0.88 | 0.52 |
| **Dense (with prefixes)** | 0.71 | 0.63 | 1.00 | 0.48 |

**What the numbers show:**
- **Hypothesis confirmed on semantic queries (`Semantic MRR`: `0.88` $\rightarrow$ `1.00`):** Adding `"query: "` and `"passage: "` prefixes resolved the remaining rank-#2 miss, placing 100% of paraphrased queries at Rank #1.
- **Unintended regression on exact identifiers (`Recall@3`: `0.79` $\rightarrow$ `0.71`, `Exact-ID MRR`: `0.52` $\rightarrow$ `0.48`):** While semantic ranking perfected, every other metric dropped—meaning more expected document IDs missed the top 3 or fell to lower ranks.
- **Why this happens:** Prefixes push the encoder to prioritize high-level sentence intent over surface-level token details. Because our `ERR_4091`–`ERR_4096` and `EXIT_137`–`EXIT_255` documents share nearly identical sentence templates, stronger semantic abstraction pulls their embeddings even closer together, causing the wrong error code to outrank the true target.

This result confirmed that no single dense configuration can maximize both slices at once—motivating our move to **Hybrid Search (Dense + BM25)** in the next experiment.


### 5.5 The Idea Behind Hybrid Search & Reciprocal Rank Fusion (RRF)

Neither retriever alone is reliable enough for production:
- **Dense (with prefixes)** achieves **1.00** on semantic understanding, but drops to **0.48** on exact IDs.
- **BM25 only** achieves **1.00** on exact IDs, but drops to **0.50** on semantic queries.

**The Hybrid Goal:** Combine both systems so we get BM25's exact-token precision for error codes and CLI flags alongside Dense's conceptual understanding for paraphrased questions.

**How Reciprocal Rank Fusion (RRF) Works:**
Dense search outputs cosine similarity scores between `0` and `1`, whereas BM25 outputs unbounded keyword scores (e.g., `0` to `15+`). Because these raw scores live on completely different scales, adding them directly would let whichever system has larger numbers dominate. RRF solves this by ignoring raw scores and combining rank positions instead—giving a high boost to documents ranked near the top (`#1`, `#2`, `#3`) and smoothly tapering off credit for lower-ranked documents:

$$
\text{RRF}(d) = \sum_{r \in \{\text{Dense}, \text{BM25}\}} \frac{w_r}{k + \text{rank}_r(d)}
$$


### 5.6 Naive 50–50 Hybrid Results & Real-World Improvements

| Experiment | Recall@3 | MRR@3 | Semantic MRR | Exact-ID MRR |
| :--- | :---: | :---: | :---: | :---: |
| **Hybrid (Dense + BM25 RRF)** | 0.93 | 0.69 | 0.75 | 0.67 |

**What the numbers show:**
- **High retrieval coverage (`Recall@3 = 0.93`):** Hybrid recovered the expected document in the top 3 for `13 / 14` queries, matching BM25's best coverage and beating Dense (`0.71`) by **+22 percentage points**.
- **Rank dilution (`MRR@3 = 0.69`, `Semantic MRR = 0.75`, `Exact-ID MRR = 0.67`):** Even though the right document is almost always inside the top 3, equal 50–50 RRF drags its rank down from `#1` to `#2` or `#3`:
  - On zero-keyword semantic queries, BM25 finds no matching words and ranks the true document near the bottom—pulling Dense's `#1` pick down (`1.00` $\rightarrow$ `0.75`).
  - On exact-ID queries, Dense confuses similar error templates and ranks the true document low—pulling BM25's `#1` pick down (`1.00` $\rightarrow$ `0.67`).

**How to Improve Hybrid Search in Real-Life Production:**
1. **Filter Zero-Match BM25 Noise:** Never let BM25 contribute a rank penalty or tie-breaker when a document has zero keyword overlap (`BM25 score == 0`), preventing irrelevant lexical misses from outvoting top semantic hits.
2. **Tune Fusion Weights to Workload Requirements:** Instead of a hardcoded 50–50 split, weight the two retrievers based on your application's query mix (for example, `0.7` Dense / `0.3` BM25 for conceptual knowledge bases, or boosting lexical weight when regex detects error codes, SKUs, or CLI flags).
3. **Add a Two-Stage Cross-Encoder Reranker:** Because `Recall@3` is already `0.93`, the candidate set is strong. Passing the top 5–10 hybrid candidates through a cross-encoder reranker (via vLLM's `llm.score()`) evaluates the query and document tokens together, pushing `#2` and `#3` hits up to `#1` and closing the gap between `Recall@3` (`0.93`) and `MRR@3` (`0.69`).

### 5.7 Complete Ablation Summary

| Experiment | Recall@3 | MRR@3 | Semantic MRR | Exact-ID MRR | Key Takeaway |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **Dense (no prefixes)** | 0.79 | 0.62 | 0.88 | 0.52 | Misaligned query/passage space; blurs numeric codes. |
| **Dense (with prefixes)** | 0.71 | 0.63 | 1.00 | 0.48 | Solves 100% of paraphrases, but worsens exact-ID collisions. |
| **BM25 only** | 0.93 | 0.86 | 0.50 | 1.00 | Perfect on exact identifiers; fails when zero words overlap. |
| **Hybrid (50–50 RRF)** | 0.93 | 0.69 | 0.75 | 0.67 | Matches peak `Recall@3` (`0.93`); exposes rank dilution fixed by zero-score filtering, tuned weights, and reranking. |

> **Benchmark Workload Note:** All 2,048 benchmark inputs used a uniform ~13-token synthetic template (`f"passage: Incident report #{i}: Postgres connection pool exhausted."`), representing ~15.8k tokens/s at peak (`batch_size = 1024`). Because `intfloat/e5-small` is a bidirectional encoder (`runner="pooling"`), vLLM executes full self-attention without KV-cache prefix reuse; on longer production chunks (`256–512` tokens), GPU saturation occurs earlier (`batch_size = 64–256`) at proportionally lower `docs/s`.

### What the Results Show

1. **Single-Prompt Overhead Bottleneck (`BS = 1` $\rightarrow$ `58.0 docs/s`):** Processing 2,048 documents one at a time takes **35.29s**. Because `intfloat/e5-small` is a lightweight 33M-parameter encoder, the GPU finishes each forward pass in sub-milliseconds while most wall-clock time is wasted in Python tokenization, vLLM scheduler dispatch, and CUDA kernel-launch overhead.
2. **Amortization & GPU Saturation (`BS = 32` to `1024` $\rightarrow$ `21.0x` Speedup):** Batching amortizes fixed per-call overhead and saturates GPU Tensor Cores via dense matrix-matrix (`GEMM`) operations. Throughput climbs from `58.0` to **1,218.7 docs/s** at `batch_size = 1024`, cutting total indexing time from **35.29s** down to **1.68s**.
3. **Diminishing Returns Beyond the Knee (`BS ≥ 256`):** Most gains are already captured by `batch_size = 256` (`1,065.7 docs/s`, `18.4x`). Pushing to `2048` (`1,130.0 docs/s`) yields no further speedup because vLLM's `--max-num-batched-tokens` scheduler internally splits oversized batches into bounded prefill chunks.

**Production Takeaway:** Use `batch_size = 1` only for real-time interactive user queries (where single-request latency matters), and batch offline document ingestion at **`256–1024` docs per call** for a **~20x throughput gain**.
