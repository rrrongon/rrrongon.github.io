To prevent silent failures—where an LLM produces fluent answers over bad context or hits hidden latency bottlenecks—the pipeline is instrumented into three distinct telemetry stages. Separating **offline ingestion**, **online hybrid retrieval**, and **grounded generation** isolates performance bottlenecks and traces answer quality back to its root cause.

### Telemetry Results

| Metric | Measured Value | Engineering Interpretation |
| :--- | :--- | :--- |
| **Model Load (`intfloat/e5-small`)** | `8.66s` | One-time cold-start overhead to initialize the vLLM pooling engine on GPU. |
| **Batch Embedding (12,084 chunks)** | `23.92s` (`505 chunks/s`, `1.98 ms/chunk`) | High GPU prefill throughput achieved by batching (`bs=256`) rather than encoding chunks sequentially. |
| **PostgreSQL Bulk Insert** | `26.27s` (`~460 rows/s`) | Writes text, parent context, SHA-256 hashes, and 384-d vectors while auto-generating `tsvector('simple')` columns. |
| **Post-Load Index Build (`HNSW` + `GIN`)** | `9.45s` (`59.64s - 23.92s - 26.27s`) | Building both indexes once after bulk insertion avoids incremental graph rebalancing and completes in under 10 seconds. |

### What These Numbers Tell Us
- **Balanced Compute & I/O Under 60 Seconds:** End-to-end ingestion of 5,183 parent documents (12,084 child chunks) completes in **59.64s**, with compute split almost evenly between GPU embedding (**40%**) and database I/O (**44%**), while post-load indexing accounts for just **16%**.
- **Zero-Redundancy Incremental Updates:** Because every row stores a deterministic SHA-256 `content_hash`, subsequent incremental runs skip unchanged chunks and incur near-zero embedding or index rebuild overhead.

### Diagnostic Breakdown of the Retrieval Scores
- **High Rank Concentration (`0.72` Recall vs. `0.69` MRR):** Out of the 36 queries where PostgreSQL found the target document, **33 landed at Rank #1** (`RR = 1.0`), **2 at Rank #2** (`RR = 0.50`), and **1 at Rank #3** (`RR = 0.33`). That minimal `0.03` gap between `Recall@3` and `MRR@3` shows that when the hybrid RRF retriever finds the right paper, it almost always places it at **Position #1**—where LLM attention is strongest.
- **Sub-5 ms Database Overhead:** At `4.70 ms` average (`6.43 ms` P95), database retrieval adds negligible latency compared to downstream LLM generation (`180.4 ms/query`).

### Telemetry & Structural Audit Results

| Span / Metric | Measured Value | What It Means |
| :--- | :--- | :--- |
| **`[MODEL LOAD]` (`Qwen2.5-3B-Instruct`)** | `26.46s` | Cold-start time to load weights and allocate KV-cache (`max_model_len=4096`) after freeing the embedding model. |
| **`[GEN SPAN]` Batch Inference (51 queries)** | `9.20s` (`180.4 ms/query`) \| `1,047.9 tok/s` | Continuous batching in vLLM sustains over 1,000 output tokens/sec across 50 SciFact queries + 1 trap query (`trap_01`). |
| **`[TOKENS]` Prompt / Output Length** | Avg Prompt: `1,281` \| Avg Output: `189` | Three full parent abstracts average ~1,281 input tokens per query, well inside the 4,096-token context window. |
| **Truncated Outputs (`finish_reason='length'`)** | `25 / 51` (`49%`) | Nearly half of the generations hit the `max_tokens=256` ceiling before emitting an EOS stop token. |
| **`[EVAL MODE 1]` Structural Pass Rate** | `0.80` (`41 / 51` passed) | 80% of responses obeyed all deterministic citation and abstention rules; 10 failed structural validation. |
| **Abstention Count** | `45 / 51` | Total responses triggering `"I cannot answer this based on the provided documents."` |

### Three Critical Engineering Insights Exposed by Observability

1. **Abstention Count (`45`) vs. Retrieval Hits (`36`):**
   Only 15 queries genuinely lacked the target document (14 retrieval misses + 1 out-of-domain trap query), yet `Qwen2.5-3B-Instruct` abstained 45 times. In `SciFact`, queries are scientific claims (many of which require multi-sentence inference or are refuted by the abstract rather than stated verbatim). Under strict closed-world prompting (*"Do NOT extrapolate beyond the text"*), a conservative 3B model defaults to abstaining whenever a claim is not explicitly confirmed verbatim—trading lower recall for near-zero hallucination.
2. **Why 25 Outputs Hit `max_tokens=256` (Avg Output: `189` tokens):**
   A clean abstention requires only **12 tokens**. Seeing an average of `189` output tokens and `25` length truncations alongside `45` abstentions reveals that the model frequently emitted the refusal phrase first, then ignored the negative constraint and appended lengthy document-by-document summaries (`[doc_id] discusses...`) until hitting `max_tokens=256`.
3. **Why 10 Traces Failed Deterministic Structural Validation (`0.80` Pass Rate):**
   Inspecting the 10 failed traces isolates two small-model formatting failure modes caught automatically at `$0` evaluation cost:
   - **Prompt-Example Leakage:** On abstentions, the model occasionally copied the prompt's placeholder ID (`[31715818]`), which regex validation immediately flagged because `31715818` was absent from `retrieved_ids`.
   - **Uncited Claims:** On non-abstaining responses, the model occasionally stated a finding from the context without attaching a bracketed `[parent_id]` citation.

## Summary: How Observability Guides the Next Iteration

By instrumenting each stage independently rather than looking at a single end-to-end accuracy number, the exact optimization roadmap becomes clear:

1. **Lift `Recall@3` (`0.72` $\rightarrow$ `0.85+`):** Over-fetch the top-20 unique parents from PostgreSQL (`4.70 ms` leaves ample latency headroom) and add a **Cross-Encoder Reranker** before generation.
2. **Eliminate `finish_reason='length'` Truncations (`25` $\rightarrow$ `0`) & Raise Structural Pass Rate (`0.80` $\rightarrow$ `0.98+`):** Add a stop sequence (`stop=["\n\n"]`) immediately after the abstention sentence and remove concrete numeric IDs from prompt examples so the 3B model cannot leak them into citations.
